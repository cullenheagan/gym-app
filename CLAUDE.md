# Gym app: working notes for Claude
- Next.js 15 + React 19 + Tailwind v4 + Supabase. Deployed on Vercel; every push to `main` redeploys.
- Commit and push straight to `main`. Write each commit message as a plain-English note on what changed and why.
- Commits are authored as Cullen Eagan (cullenheagan@gmail.com) with a `Co-Authored-By: Claude` trailer. Set this with `git config user.name/user.email` in the clone.
- Keep the history clean: one commit per finished feature or fix, not one per small edit. Batch related edits, typecheck, then commit once. Do not push half-done work or tiny follow-up commits; fold them in before committing.
- Ask Cullen before deciding anything about look, branding or wording: logo and icons, colors, fonts, names, layout changes, and similar. Show options first (images when it helps), and change nothing until he picks. Same for any other decision he would want a say in.
- For each change: add an entry to `CHANGELOG.md` and to the Changelog page in the Notion "Gym App" wiki. Update the Features and Database pages when they change.
- New database changes go in a new numbered file under `supabase/migrations/`. The Supabase connector is available (project `gym-app`): show the SQL, ask before anything that changes or deletes existing data, apply it with the connector, then run the security advisor. If the connector is not available, tell the user to run the file in the Supabase SQL Editor before using the feature.
- Grants (Supabase stops auto-granting Data API access to new `public` tables on Oct 30, 2026): every migration that creates a table must also add explicit grants in the same file: `authenticated` gets only the operations the app uses, `anon` gets nothing (the app requires sign-in), `service_role` gets what it needs. Keep RLS on. After applying, check the app for "permission denied". Tables 0001 to 0021 predate this and keep their existing grants; a consolidated grants migration is only needed if the database is rebuilt (for example a separate demo project).
- Weights are stored in kg and converted for display. Look: light/dark tokens in `src/app/globals.css`.
- Typecheck before pushing (`npx tsc --noEmit`).

- My plan (HCI class proof of concept, team 2CNE; proposal requirements F2 to F5, F7 and part of F8): a separate beginner app, not part of Train. "New to the gym? Get a plan" on the sign-in screen signs in anonymously with user_metadata.mode = "beginner"; App renders only src/components/MyPlan.tsx for those accounts (no sample data, no Train/Nutrition). Logging there is a checklist plus "Mark today done", which inserts a workout row with no sets (what the weekly goal counts). Beginner accounts are deleted after 30 days without use, demo guests after 7 days (delete_old_guests, migration 0025). Questionnaire and generator in src/lib/plan.ts (pure, tested by tests/plan.test.ts via `npm test`, every answer combination); exercises in src/lib/exercise-library.ts (all 40 have a demo video chosen by the team, listed in docs/exercise-videos.md; check a new link embeds before adding it); saved in the plans table (migration 0023). Rules: at least one rest day, no muscle group on consecutive days including Sunday into Monday. Keep the tests passing when changing the library or the plan rules. F7 goals: a weekly workout goal (Cullen chose this type only) in the Goals card on My plan (src/components/GoalsCard.tsx, logic in src/lib/goals.ts, tests/goals.test.ts, goals table from migration 0024; editing ends the old row and adds a new one so past weeks keep their goal).
- Guest demo (migration 0022): "Look around as a guest" uses Supabase anonymous sign-in (dashboard switch must stay on); App calls seed_guest_data() once before opening the app. Guests can't upload photos, see a note in Settings, and are deleted after 7 days by the pg_cron job delete-old-guests. When adding tables or features, make sure the sample data still makes sense and that delete_old_guests still removes everything a guest can create.
